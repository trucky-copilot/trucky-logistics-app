# Existing billing companies: reuse the same org, do not duplicate

This extends the staged patch, not the legacy Testing-Pro one-time migration. It does NOT turn on general billing or paid operational access. Default flags for new endpoints remain OFF; no new secret values required.

## Existing/native companies
`enrollExistingBillingOrganization` is an admin-reviewed THREE-stage flow on the same existing member/org, no company creation:
1. Landing `/billing-link/existing` requests a fresh Google login and consent. User supplies exact org/member IDs provided by operator (they are candidates, not authority). Backend calls function mode `owner_approval` using TRUCKY_SERVER_SECRET and protected Google ID token. Base44 verifies JWKS/RS256/issuer/audience/exp/iat<=10 min and current active single owner. It records a 10-minute Google approval WITHOUT token and returns a random request ID. No membership changes. Email comparisons are cross-checks/candidate filtering only, not enough to enroll.
2. Fixed native app destination uses fragment `billing_existing`, org/member IDs, captured before routing and immediately removed from the address bar. ExistingBillingConsent obtains actual native session, displays it and requests explicit consent. Function mode `request` consumes the Google approval once only if the native/Google emails cross-check and no existing Google/native binding conflicts. It records both authenticated IDs with a 15-minute approval for administrator. Request ID is not an ID token or server credential; no copying of Google tokens, URLs or native sessions.
3. A server-allowlisted admin with role admin uses `preview` then `execute` (never receives a token). Body includes org/member IDs, request_id; execute adds confirm `ENROLL <member-id>`, ownership_verified:true and evidence_reference (8–120 chars, case/audit reference, NO tokens/emails/freeform secrets). Admin MUST independently verify native ownership in server-created records/account history. If independent evidence is unavailable, reject/retain for review — matching email is NOT a substitute. This manual admin-authorized enrollment is not automatic email takeover. A request may not change an already populated different google_sub/base44_user_id.
Execution consumes approval with audit first, conditionally updates exact member id + prior Google/native values + active owner role using updateMany, checks updated===1, then atomic proof+enrollment registration. It never creates global native/Google identity keys; owner uses ordinary `/billing-link` confirmation afterwards to create/check those. Unknown/partial execution returns EXISTING_ENROLLMENT_REQUIRES_REVIEW, no auto retry/delete. Admin must read audit + member/proof/enrollment and conditionally complete the SAME pair after determining result; no fresh company or overwriting conflict. Preview/read-only shows reviewed IDs only to admin.

Flags: BILLING_EXISTING_ENROLLMENT_ENABLED defaults false in landing and Base44. BILLING_EXISTING_ENROLLMENT_ADMIN_IDS in Base44 (role admin AND listed). Separate from new public signups; closing signups must not disable existing registered webhook/link recognition. Existing company enrollment and paid access are not turned on by adding these routes. Use reviewed native/backend publication before landing.

## Creation diagnostic (no release)
POST `inspectBillingCreation` from authorized native admin session. Flag BILLING_CREATION_INSPECTION_ENABLED default false; BILLING_CREATION_INSPECTION_ADMIN_IDS role+list restriction. Body `{google_sub,company_name}`. It derives exact billing reservation key; reads it and active memberships/orgs. Returns presence, whether final org ID matches, candidate org/member IDs and `no_automatic_release:true`. No credential/token/key values logged; no DEL, no SET, no Organization update. Absence of candidate members does not prove no orphan org or in-flight write: operator checks provider audit and exact known creation timestamps/IDs. There is intentionally NO automated release when a request could still land. Known-completed creation may be finalized only through owner-checked reviewed flow; uncertain outcome retained. No blind Redis edits.
