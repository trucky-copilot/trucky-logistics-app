# V3: paid chat credit and paid upgrade — apply after v1+v2

Business decisions: chat quota restarts on each confirmed subscription payment, not a calendar timer; upgrade benefits only after payment. Plan29=1000 requests; plan99=2000, shared by canonical org/subscription. No new production variables, no flag enabling, no charges, no changing historical subscriptions/demo dates.

## Stripe evidence and paid plan
Server runtime retrieves actual live subscription AND paid invoices from Stripe, scoped to that subscription. It independently validates invoice real mode, paid status, positive amount paid, same sub/customer, approved reason (create/cycle/update), complete lines, a single positive line of quantity 1 and one authorized price, and an integer paid_at. It selects the latest paid_at (a same-second tie between distinct invoices rejects for review). Multiple positive invoice lines, zero-dollar coupons/invoices, or paginated line sets are conservatively unsupported; no guessing. At most the 100 recent paid invoices are examined; older credit is not fabricated. These constraints need business acceptance; current USD 29/99 single-subscription-item model only.

The subscription itself must still be real/active, same company/customer, one item with approved USD monthly price, no active/future trial. A paid historical price can remain effective while an upgrade invoice is open: previous paid plan/credit stays, no higher benefits until paid upgrade invoice appears. Failure to find any valid paid invoice -> no paid access. Canceled/past_due/unpaid/etc remains denied. Renewal invoice draft/open does not destroy prior credit while status stays active. API permission required for invoice reads in addition to subscription reads; operator checks restricted key permission via Stripe; don't blindly grant full access. Do not log invoices/keys.

Pure validateLivePlan compatibility path now requires paid invoice for subscription_update as well as initial payment. Actual runtime always derives verifiedPaidCredit from the paid-invoice list, never from request body. The 5-second cache and bounded transient grace of v2 remain; new payment/upgraded limits can take 5 seconds to appear. No direct browser-supplied quota or plan accepted.

## Atomic consumption
liveChatQuota.ts invokes one Lua operation with an org/sub current-invoice high-water key and per-paid-invoice hash. Keys under trucky:billing:quota:live:<org>:<sub>. Reusing the same paid invoice never resets used. A later paid_at transitions exactly once to a different invoice ledger (fresh quota). A stale or tied distinct invoice cannot switch back and regain old allowance. Requests get a UUID from the chat frontend; backend reserves one message after body validation before AI/data work. Reusing same UUID is rejected rather than invoking AI twice (not cached-response replay). Redis uncertain/failed -> no authorization for consumption; no auto-refund or deletion. Failed AI after reservation currently conservatively consumes one request; no claim of billable-success metering. Requests are per native user action (one chat call), not each historical message in the request array.

All ledger records have no TTL to prevent late webhook/retry double-grant or usage reset; plan for reviewed archival and memory monitoring (up to one hash field per allowed call). Don't clear these keys to "fix" quota. Current script sets high-water before adding a request. A failed request may leave the new current invoice set but cannot erase prior usage, and retry same invoice uses its ledger; no unconditional reset. Full script must be tested against actual Redis by operator for 1000/2000 boundary, duplicate UUID, simultaneous requests at limit, paid renewal/upgrade once, stale and same-second invoice. Lua execution here used a local Lua interpreter with mocked Redis hash primitives, NOT Redis cloud. It proves script branches not platform delivery/persistence. No real Redis/customer writes executed by Agent.
