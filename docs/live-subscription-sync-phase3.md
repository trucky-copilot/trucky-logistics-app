## Serialization and uncertain writes
A dedicated backend lock trucky:billing:sync:live:org:<org> is acquired with SET NX before org reads and Stripe retrieval. Different from the Vercel webhook lock, avoiding deadlock on a nested request. No TTL: do not auto-release an unknown DB write. Successful update or errors before writing release only their own lock via Lua. Before updating Base44 the function records `trucky:billing:sync:live:pending:org:<org>` = {owner, orgId, subscriptionId, fields, before, startedAt} (no tokens). A successful write releases lock and its own pending record atomically (Lua, owner-checked). A DB write timeout returns LIVE_WRITE_REQUIRES_REVIEW and retains BOTH lock and pending record; live provider/Redis failures can be uncertain, so inspect records before operator recovery. The function does not retry writes. Duplicate completed calls fetch latest state again and set the same isolated fields; no event timestamp overwrites cached state. This is not durable invoice/event history.

## Administrative lock recovery (`recoverLiveSyncLock`)
Never a blind delete, and never a release without evidence that no write can still land. Native Base44 admin session only (role `admin` AND listed in `BILLING_SYNC_RECOVERY_ADMIN_IDS`); switch `BILLING_SYNC_RECOVERY_ENABLED` defaults OFF. Never accepts the S2S secret or tokens, never writes Organization, never retries the sync.

Fencing in the sync: the pending record is written with `SET_PENDING_IF_OWNER_SCRIPT` (only if the caller still owns the lock), and Base44 is updated only after that. A process whose lock was released can therefore never record or perform its write (`LIVE_LOCK_LOST`).

- `{"mode":"preview","organization_id":"<org>"}` → `RECOVERY_PREVIEW` (no writes) with `owner`, `ageSeconds`, `subscriptionId`, `canRelease` and `outcome`:
  - `NO_WRITE_STARTED`: lock without pending record. Releasable (fencing guarantees the owner can no longer write; the release script also checks atomically that no pending record appeared).
  - `WRITE_APPLIED`: the Organization's `stripe_live_sync_operation_id` equals the pending owner (this operation's unique id) AND the 5 live fields equal `pending.fields`. The sync writes the id in the SAME single `update` call as the 5 fields, so only that write can leave it. Releasable.
  - `WRITE_NOT_APPLIED_YET`: this operation's id is not on the record. Field equality alone is NOT proof of completion (when `before === fields` the record already looks "applied" while the write may still be in flight and land after a cancellation). **Not releasable**: the lock is kept; re-check later. Only the operation id + matching fields (outcome `WRITE_APPLIED`) allows release. While the lock is held, no other sync can write.
  - `WRITE_PARTIAL`: the id is present but the fields differ → manual review.
  - `ATOMICITY_NOT_PROVEN`: the pending record does not declare `writeMethod: "updateMany:$set:single-id"` (e.g. left by an earlier version) → no proof; not releasable.
  - Atomicity evidence: the write is `Organization.updateMany({id},{$set:{...5 fields, stripe_live_sync_operation_id}})`, not `update()`. Base44's SDK reference for `updateMany` states that "all the update operators in a call … are applied to each record in a single write", and that conditions are re-checked at write time when the query names a single `id` (`@base44/sdk` 0.8.59 `dist/modules/entities.types.d.ts`; the 0.8.54 client used by the functions sends the identical `PATCH …/update-many` request). `update()` documents no such guarantee, so it is not used. The sync only treats the write as done if Base44 answers `updated === 1`; any other answer keeps lock and pending. This is vendor-documented behavior, not a test executed against Base44: if that guarantee is withdrawn or cannot be confirmed, `WRITE_APPLIED` must be treated as not releasable and the lock kept.
  - `WRITE_PARTIAL` / `INCONSISTENT`: manual review; never released by this function.
- `{"mode":"release","organization_id":"<org>","owner":"<owner from preview>","confirm":"RELEASE <org>"}` requires exact confirmation, the same owner as reviewed (`OWNER_MISMATCH`) and a releasable outcome (`WRITE_NOT_APPLIED_YET` / `REVIEW_REQUIRED` otherwise). A 5-minute minimum lock age (`LOCK_TOO_RECENT`) is an operational courtesy, not a safety guarantee.
- Audit and release are ONE atomic Redis operation (`RECOVERY_RELEASE_SCRIPT`): it re-checks owner and pending state, then `RPUSH`es the audit entry to `trucky:billing:sync:live:recovery:audit` BEFORE deleting lock and pending. If the audit write fails the script aborts and nothing is released (`RECOVERY_REQUIRES_REVIEW`). There is no release without a durable audit record. `LOCK_CHANGED` if the owner changed meanwhile.
