# Live checkout pilot readiness — no charge authorized

Base main 058efe8c7c96b6fcbeb2e7439e58c292d09e4f30 (phase 3 merged). Current resolver ignored mode and returned test subscription state, so linked Testing-Pro with historical test billing could not safely represent a first live subscription. This patch separates resolver state by explicit mode and adds an authenticated read-only eligibility check.

Publish on separate reviewed PR, no wholesale historical branch merge. Keep STRIPE_MODE=test, live payment/webhook/enforcement/recovery switches OFF. New BILLING_LIVE_CHECKOUT_ELIGIBILITY_ENABLED defaults OFF. Schema and phase-3 sync are prerequisites. No organization/customer/subscription creation, update or Redis mutation in these changes. No new secrets required.

## Functions
- resolveUserOrganizations: missing mode remains test; explicit live returns mode:live, isolated stripe_live_* status/plan and first-live-subscription can_checkout; does NOT grant access. Live requests gated by BILLING_LIVE_CHECKOUT_ELIGIBILITY_ENABLED. Existing test handling remains. Resolver still validates Google as previously implemented; this patch does not certify or refactor that authentication implementation.
- checkLiveCheckoutEligibility (entry.ts, eligibility.ts, demoRegistry.ts, provenance.ts): POST requires TRUCKY_SERVER_SECRET bearer and {google_sub,organization_id} only from trusted landing backend. Browser must never supply google_sub as proof; landing derives it from its protected authenticated session. Both BILLING_LIVE_CHECKOUT_ELIGIBILITY_ENABLED and BILLING_SYNC_LIVE_ENABLED must be true for success; otherwise 503 LIVE_CHECKOUT_NOT_READY. Server pilot lists constrain exact org/member; validates active billing membership/provenance, both identity mappings, org active and absence of ALL live records. Test records do not block live. Existing live mapping (even canceled) returns 409 ALREADY_SUBSCRIBED; resubscription/upgrades are out of scope.

Restore backend flags OFF after acceptance. Do not call sync with an actual live subscription during this read-only check.

## Follow-up review corrections
- Backend eligibility checks EXISTS on BOTH phase-3 lock and pending before returning eligible; nonzero returns 409 LIVE_RECONCILIATION_PENDING, errors fail closed. This is a read-only point-in-time check, not a substitute for mutation locks during checkout and reconciliation.
- HTTP entry uses a testable request handler: missing/incorrect bearer 401, either switch off 503 before SDK creation, invalid JSON/null/array/missing or extra fields 400. Resolver rejects invalid JSON bodies/modes and gates live before Google/DB calls. Test projection is identical with absent mode; a prior test subscription alone projects live none/can_checkout:true.
- Resolver can_checkout:true is NOT proof of pilot eligibility or permission to open live Checkout; the separate authenticated check must succeed for the exact linked pilot.
- Landing, while holding its persistent live checkout mutation lock, searches Stripe live subscriptions by metadata.org_id without excluding canceled states. ANY existing match blocks first-live purchase; API errors or unsupported Search block. It then repeats backend eligibility before reserving. Stripe Search is eventually consistent, so a missing result is NOT evidence that a prior unknown payment did not exist; do not remove/release earlier uncertainty locks. Operator must inspect known prior live attempts before first controlled purchase. No automatic recovery/resubscription based on Search absence.
- Acceptance: keep any temporary enabling of BILLING_SYNC_LIVE_ENABLED short, exact pilot lists, Vercel live webhook AND checkout flags false throughout. Restore backend flags false after collecting read-only eligibility evidence. No charges, no admin data entry, no Redis writes from these two functions.
- Added 8 Node core/HTTP/projection tests plus one Deno actual resolver entry test for invalid body/mode and live-off guards; original live happy-path resolver/projection tests use dependency-free helpers, not a real Google login. Platform E2E remains operator work.
