Not deployed; no flag activation. All runtime review/acceptance boundaries of previous document remain. This document supersedes the previous description of DemoContext polling, invoice criteria and retry/cache behavior.

## UI and demo isolation
DemoContext.jsx is restored BYTE-FOR-BYTE to main 125c31b. AppContent's original demo logic is retained except that verified live-paid users bypass the demo-expiration screen; do not bypass native auth or onboarding. LivePlanProvider is separate, inside native auth and AppState, outside ProfileProvider; it loads on session initialization only. Focus/minute updates never set global loading or loadingTrial. managed:false stops network polling for this provider session, including focus; a new native login/provider mount starts a new session. Transient errors show a non-blocking notice, retain the last result and never relabel the demo expired. An explicit prior denial remains a denial. Backend operations still fail closed if no verified recent result is available.

UI consumers (profiles, chat, fleet, drivers, broker, loads, documents, emails and layout) use useEffectivePlan, composing existing demo defaults with verified real plan, without rewriting DemoContext. The LivePlanBoundary blocks only managed denied accounts. A first-query error cannot prove managed status and is not treated as subscription denial; this does not authorize protected server operations. Shared backend gates remain authoritative. No new LiveBillingGate from historic branch.

## Renewal policy
An expanded, linked real invoice is validated against the same subscription/customer. Initial invoice billing_reason=subscription_create must be paid. With billing_reason subscription_cycle or subscription_update, a real subscription still active is sufficient; draft/open renewal invoices don't interrupt access. Once Stripe status becomes past_due/unpaid/canceled/etc, deny (no new grace policy). Unknown invoice reason, missing invoice or foreign invoice fail closed. No trial or test subscription grants real plan. No assumption that active proves an individual invoice was paid; the distinction is deliberate. This policy must be approved by business before enabling.

## Server cache and revocation bound
Per worker, maximum 1000 entries, key includes native id/email and server-configured price IDs. No secrets/tokens or cross-user reuse. Coalesces concurrent reads. Normal TTL 5s avoids repeated Redis/Stripe lookups on each message. A Redis/provider availability error or normal LIVE_SYNC_PENDING may reuse ONLY a previously verified allowed result younger than 30s TOTAL. Such reuse does not extend original timestamp. No prior result -> no authorization. Explicit denial replaces prior allow; identity/provenance mismatch errors cannot use grace fallback. Disabled enforcement bypasses cache, network and DB checks. Cache is local best-effort, not durable, and may be empty on another function worker/cold start. Normal pending without previous proof remains denied, not fake success. Known revocation latency max 5s normal or 30s during availability degradation; business/operator must accept this before enabling. No unconditional fail-open or indefinite stale results.
